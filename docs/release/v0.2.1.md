# passalong v0.2.1

Draft for the `v0.2.1` tag, from the branch `feature/00009-v0.2.1`.
Delivered by
[Delivery Plan 00009](https://github.com/joelee/passalong/blob/v0.2.1/docs/plans/00009-V0_2_1_Windows_And_Review_Fixes.md).

## Summary

- **Windows:** passalong runs on Windows x86_64. That covers the commands,
  `serve` in the background, and start at log-in through the Run key or
  Task Scheduler. Key files stay private to their owner. A release zip is
  published.
- **Safer encryption changes:** every finding of the
  [v0.2.0 review](https://github.com/joelee/passalong/blob/v0.2.1/docs/reviews/00002-V0_2_0_Release_Review.md)
  is fixed. Nothing can publish under a replaced key, and a partly synced
  encrypted store is never taken for a plaintext one. Every change of
  encryption is locked and journalled, so it can be finished or undone.
- **Compatible:** the store layout and the library API are unchanged
  (additions only), and v0.2.0 and v0.2.1 work with the same stores.

## Changes

### New in v0.2.1

- **Windows x86_64.** Settings live in `%APPDATA%\passalong` (system-wide:
  `%ProgramData%\passalong`), `serve`'s files in `%LOCALAPPDATA%\passalong`,
  and `~` is `%USERPROFILE%`.
- **`serve --daemon`, `--status`, and `--stop` on Windows.** The background
  `serve` has no window. `--stop` asks it to stop through a `serve.stop` file.
- **`service-install` on Windows** adds `serve --daemon` to the per-user Run
  key, with no administrator needed. With `--scheduler` it registers a Task
  Scheduler log-on task that restarts `serve` if it fails; that needs an
  administrator prompt. `service-remove` removes either. Neither is a
  Windows service, because services cannot reach the clipboard.
- **`encrypt --recover`** also finishes or undoes an interrupted set-up,
  fresh start, or change of words. It restores a store whose header an
  interrupted v0.2.0 change left aside, once the words unlock it.
- **`check` and `list`** report what v0.2.0 left unencrypted in `tmp/` when
  it encrypted a store; `prune --plain` removes it.
- **File names** from the store are made safe for Windows on every
  platform, so a file sent from Linux or macOS downloads on Windows.

### Fixed

- A send that raced a key rotation could store an item that only the old
  key opens. The header's key id is now read before every write and again
  after publishing; a raced send takes its item back and fails, and `serve`
  sends the file again later. (MAJ-01, MED-02)
- A synced folder that delivered only part of an encrypted layout could be
  opened as a plaintext store and written to. Any such part now makes the
  store broken, never plaintext, and an open plaintext store stops writing
  once encryption starts. (MAJ-02)
- Uploads cut short before a store was encrypted could leave plaintext in
  `tmp/`. Encrypting now removes it. (MAJ-03)
- Setting up encryption, a fresh start, and changing the words were not
  locked or journalled, so an interruption could leave a store without a
  usable header. They now use the lock and journal of a re-encryption.
  (MAJ-04)
- A cut-short start of a re-encryption could leave a lock with an empty
  journal. The journal is now written whole before it becomes the lock.
  (MED-01)
- `serve`'s list cache kept the old key's identity across a migration or
  rotation, and pull mode stopped at an encrypted item that did not open.
  (MED-03, MED-04)
- The key file's git check followed the path as written, not through
  symbolic links. (MED-05)
- The v0.1.6 compatibility test did not run v0.1.6's real `prune`, and the
  v0.2.0 notes claimed a synced-folder check that was not made. (LOW-01,
  LOW-02)

## Security

- On Windows the key file, the folders created for it, and the list cache
  are open to their owner alone. passalong sets that with `icacls`, and
  refuses a key file others may open, naming the command that fixes it.
- A device with a rotated-out key can no longer add items under that key,
  even when a send races the rotation.
- Plaintext is never written into a store that is being encrypted, and no
  plaintext staging is left behind by encrypting.

## Configuration

No new settings. On Windows the default locations are those above; see
[configuration](https://github.com/joelee/passalong/blob/v0.2.1/docs/configuration.md).

## Library changes

Additions only; `cargo semver-checks` finds no breaking change in
`passalong-core` or `passalong-ssh` against 0.2.0.

- In `passalong_core::encryption`: `Journal`, `HeaderChange`,
  `HeaderChangeKind`, `read_journal`, `RecoveryMarker`,
  `RECOVERY_STALE_SECS`, `recovery_in_progress`, `release_recovery`,
  `restore_header`, `Leftovers`, `leftovers`, and `remove_leftovers`.
- `ListCache::identity_for`.
- `RemoteFs` for `Arc<T>`.

## Upgrade notes

- v0.2.0 and v0.2.1 read and write the same stores; a v0.2.0 device keeps
  working with a store v0.2.1 encrypted, re-worded, or rotated.
- If v0.2.0 encrypted a store, `passalong check` reports anything it left
  unencrypted in `tmp/`; `passalong prune --plain` removes it.
- On Windows, use PowerShell. Piping binary data into or out of passalong
  (`passalong cat <ID> > photo.png`) needs PowerShell 7.4 or later; with
  Windows PowerShell 5.1 use `passalong load <ID> photo.png`.

## Known limitations

- **One device changes encryption at a time.** On a synced folder, two
  devices can each take the lock before their copies sync. Run `encrypt`
  and `encrypt --recover` on one device while the others are idle and in
  sync.
- **Lost writes are not covered.** Recovery covers an interrupted client,
  not storage that loses writes it acknowledged, such as after a power
  loss on the storage host.
- **Windows:**
  - The Task Scheduler task's console window stays open while `serve` runs.
  - The Run key does not restart `serve` after a crash.
  - Only x86_64 is built.
  - Windows was tested on GitHub's Windows runner; the check on a Windows
    10/11 desktop is the maintainer's.
- An encrypted store cannot be turned back into a plaintext one.
- Creation times, item counts, and sizes stay visible to the storage.
- No synced-folder provider was tested; the two-device check is in the
  backlog (v0.2.2).
