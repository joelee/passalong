# passalong v0.3.0

Draft for the `v0.3.0` tag, from the branch
`feature/v0.3.0-passalong-server` and its pull request to `main`. Delivered
by
[Delivery Plan 00010](https://github.com/joelee/passalong/blob/v0.3.0/docs/plans/00010-V0_3_0_Passalong_Server_Backend.md).
GitHub release: <https://github.com/joelee/passalong/releases/tag/v0.3.0>.

## Summary

- **A passalong-server as the store:** besides an SSH server and a
  `local` folder, a device can use a workspace on a
  [passalong-server](https://github.com/joelee/passalong-server), reached
  over HTTPS with an API key of its own. Every command works with it, and
  items keep the same bytes as in any other store.
- **Encryption works the same:** a workspace can be encrypted, joined,
  re-worded, migrated, and rotated. The key stays on the devices, and the
  server stores only sealed items. An interrupted re-encryption can be
  finished or undone from any device once its holder's lease ends.
- **Compatible:** the SSH and `local` store layouts are unchanged, and
  v0.2.x devices keep working with them.

## Changes

### New in v0.3.0

- **The `https` backend.** `kind = "https"` with a `[server.https]`
  section: `url`, `tls_pin`, and `api_key_file`. Items are uploaded in
  three steps the server can replay safely, and downloads that break off
  resume where they stopped, up to three times.
- **TLS.** With `tls_pin`, the SHA-256 of the certificate's public key,
  that key alone is trusted: this is how a self-signed server works, and
  the pin survives a renewal with the same key. Without a pin, the
  operating system's certificate authorities decide. Nothing turns
  verification off.
- **`passalong init` for a server.** It asks the kind of server first,
  then the URL. It shows the pin of the certificate the server presents,
  found by a handshake that sends no request, and has you paste the pin
  `passalong-server tls fingerprint` prints on the server. The API key is
  typed without echo and saved readable by you alone. Before anything is
  written, `init` shows the key's role and expiry and what the server says
  about the workspace. `--backend`, `--url`, `--tls-pin`, and
  `--api-key-file` make it scriptable.
- **`passalong check` for a server** adds three lines. `server` shows the
  version, API version, and TLS mode. `api key` shows its label, role, and
  expiry, with a warning from 14 days before it expires. `workspace` shows
  the bytes used out of the quota and the item count. A read-only key is
  reported rather than probed.
- **Encryption with a server.** `encrypt` sets up, joins, changes the
  words, starts fresh, migrates, and rotates. Set-up, a fresh start, and a
  change of words are each one atomic call. Migration and rotation run the
  same engine as on a filesystem: every item is copied under the new key,
  read back and compared, and then committed at once. The server keeps
  the session, and a background task renews its lease while it runs.
- **`encrypt --recover` with a server.** It shows the open session, who
  holds it, and until when. The holder finishes it with the new words or
  undoes it. Another device can take it over once the lease has ended, ten
  minutes by default; a rotation also needs the old key or the old words.
- **`serve` with a server.** It waits out another device's re-encryption
  and sends afterwards. On a key change it keeps the file and asks for
  `encrypt --join`. When the API key has expired or was revoked, it stops
  with the server's reason, and a file not yet sent stays in the drop
  folder. The list cache and pull mode cover servers.

## Security

- The API key is a bearer credential. It is kept in an owner-only file,
  refused if others can read it or if git would commit it. It is sent only
  over verified TLS, never shown, and redacted from debug output.
- A request refused for its key (`UNAUTHENTICATED`, `KEY_EXPIRED`,
  `KEY_REVOKED`) is never repeated, so a wrong key cannot lock out the
  other devices behind the same address.
- A device with a key never sends plaintext, whatever the server says
  about the workspace. A new device without one confirms a "not encrypted"
  claim during `init` before anything is written.
- Every write names the key id the device expects, and the server refuses
  writes under a replaced key. Every item read is opened and checked on
  the device, as with the other stores.
- Before a rewrite begins, the device checks that the new header opens with
  the new words, so a commit cannot lock the workspace.

## Configuration

A new `[server.https]` section: `url` (`https://` only), `tls_pin`
(`sha256/<base64>`, or `curl`'s `sha256//` form), and `api_key_file`
(default: `api.key` beside the config file). `serve.list_cache` now covers
`https` stores too. See
[configuration](https://github.com/joelee/passalong/blob/v0.3.0/docs/configuration.md#serverhttps-required-when-kind--https).

## Library changes

New crate `passalong-https`: `HttpStore`, `HttpEncryptionAdmin`, `Client`,
`tls` (`client_config`, `PinnedVerifier`, `presented`, `spki_pin`), the
API types in `api`, and `register` for a `BackendRegistry`.

In `passalong-core`, additions:

- `api_key`: `ApiKey`, `ApiKeyError`, `load_api_key`, `save_api_key`, and
  `check_api_key_location`;
- in `config`: `HttpsConfig`, `TlsPin`, `HttpsInitAnswers`,
  `render_https`, `API_KEY_FILE_NAME`, and `default_api_key_path`;
- `store::format`: the `meta.json` and content bytes every store writes;
- in `encryption`: the `EncryptionAdmin` and `Rewrite` traits,
  `run_rewrite`, `FsEncryptionAdmin`, `OpenRewrite`, `HEARTBEAT_EVERY`,
  `Claim`, and `opening`;
- `BackendRegistry::open_admin` and `register_admin`, with `AdminFuture`
  and `AdminOpener`;
- `StoreError::Denied`.

Breaking, found by `cargo semver-checks` against 0.2.1:

- `KeyFileError::InGitWorkTree` and `GitUnavailable` gain a `setting`
  field, and `Damaged` a `what` field, so each message names the key file
  or the API key file.
- `ServeError::Denied` and `JobOutcome::Denied`, for a store that refuses
  the device for good; neither enum was `#[non_exhaustive]`.

`passalong-ssh` has no breaking change.

## Upgrade notes

- SSH and `local` stores need nothing: their layout is unchanged, and
  v0.2.x and v0.3.0 devices share them.
- Interactive `passalong init` now asks first whether the server is `ssh`
  or `https`; pressing Enter keeps SSH.
- Finishing another device's re-encryption needs a passalong-server at or
  after commit `d565a28`, whose rewrite sessions carry the new header. The
  tests run against that commit.

## Licence boundary

passalong-server is AGPL-3.0-or-later and passalong Apache-2.0. The client
was written from the server's published API documents alone. No code of
the server was copied, and no crate of it is a dependency: `cargo tree`
for the workspace lists none. The tests only run a server binary built
from its repository.
